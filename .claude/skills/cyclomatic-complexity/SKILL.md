# 循環的複雑度・認知的複雑度の管理（Cyclomatic & Cognitive Complexity）

`hayabusa` では、超高速なシステムコードでありながら「人間と AI の双方が一目で制御フローを追える保守性」と「JIT コンパイラの最適化（インライン化・レジスタ割り当て）が効きやすい小さなメソッド構造」を両立するため、複雑度を厳格に計測・制限します。

## 1. 閾値（Thresholds）と品質ゲート

手書きコード（Source Generator が自動生成する `*.g.cs` を除く）に対して、以下の上限を設けます。

| 指標 | 理想値 | 警告（要リファクタ検討） | 上限（ビルドエラー / PR ブロック） |
| --- | --- | --- | --- |
| **循環的複雑度 (Cyclomatic Complexity)** | 1 〜 5 | 6 〜 7 | **8 以上は禁止**（最大許容 **7**） |
| **認知的複雑度 (Cognitive Complexity)** | 0 〜 6 | 7 〜 9 | **10 以上は禁止** |
| **ネスト深度 (Max Nesting Depth)** | 0 〜 2 | 3 | **4 以上は禁止** |
| **メソッド行数 (Executable Lines)** | 〜 25行 | 26 〜 40行 | **45行超は分割必須** |
| **引数の数 (Parameter Count)** | 0 〜 3 | 4 | **5個以上は `readonly struct` にまとめる** |

> **Source Generator 生成コードの扱い**:
> `Hayabusa.Generator` が出力するファイルには先頭に `// <auto-generated />` を付与し、ジャンプテーブル（大規模 `switch`）の複雑度チェック対象から除外します。ただし **Generator 自身の実装コード** には上記閾値を厳格に適用します。

## 2. 計測方法（Measurement）

### 2.1 Roslyn Analyzer / `.editorconfig` による常時検査

プロジェクトルートの `.editorconfig` および `Directory.Build.props` に以下を組み込み、`dotnet build` 時に自動計測します。

```ini
[*.cs]
# CA1502: Avoid excessive complexity (標準アナライザ + カスタム閾値)
dotnet_diagnostic.CA1502.severity = error
# CA1505: Avoid unmaintainable code
dotnet_diagnostic.CA1505.severity = error
# CA1506: Avoid excessive class coupling
dotnet_diagnostic.CA1506.severity = warning
```

さらに精密な閾値強制のために、以下のいずれかのアナライザまたは CLI ツールを CI / ローカル検証で使用します。

1. **Roslyn ベース検査**:
   - `SonarAnalyzer.CSharp`（`S1541`: Cyclomatic Complexity、`S3776`: Cognitive Complexity）を `Threshold = 7` で有効化。
2. **CLI による定量計測**:
   - Python 環境がある場合: `npx` または `lizard -l csharp -C 7 src/` を実行し、全メソッドの CCN（Cyclomatic Complexity Number）一覧と違反ゼロを確認する。
   - .NET ツール: `dotnet-counters` / Roslyn SyntaxWalker スクリプトによるブランチノード（`if`, `else if`, `switch` arm, `for`, `foreach`, `while`, `&&`, `||`, `?:`, `??`, `catch`）のカウント。

### 2.2 手動・コードレビュー時の簡易計算式

$$\text{CCN} = 1 + (\text{分岐・ループ・論理演算子の数})$$

カウント対象（各 $+1$）:
- `if` / `else if`
- `switch` の各 `case`（または switch 式のアーム）
- `for` / `foreach` / `while` / `do`
- `catch`
- 条件式内の `&&` / `||` / `?:` / `??`

## 3. 複雑度を下げる実践テクニック（パフォーマンスを犠牲にしない手法）

システムプログラミング（パーサや状態機械）は素直に書くと `if-else` や `switch` が肥大化しがちです。`hayabusa` では以下のパターンで複雑度を抑えつつ高速化します。

### パターン1: ガード節のフラット化 + `[MethodImpl(MethodImplOptions.AggressiveInlining)]`

ネストした条件分岐は、早期リターンと小さな `private static` ヘルパーメソッド（インライン化指定）に分割します。メソッドを分割しても `AggressiveInlining` により実行時オーバーヘッドはゼロです。

```csharp
// Bad: ネストが深く CCN が高い
public bool ProcessFrame(ReadOnlySpan<byte> buffer, out RpcHeader header)
{
    if (buffer.Length >= RpcHeader.Size)
    {
        if (buffer[0] == RpcHeader.MagicByte)
        {
            // ... さらに条件分岐 ...
        }
    }
    header = default;
    return false;
}

// Good: フラットなガード節 + 単一責務ヘルパー (CCN = 3)
public bool TryReadHeader(ReadOnlySpan<byte> buffer, out RpcHeader header)
{
    header = default;
    if (buffer.Length < RpcHeader.Size) return false;
    if (!IsValidMagic(buffer[0])) return false;

    header = ParseHeaderUnchecked(buffer);
    return true;
}
```

### パターン2: 分岐のテーブルルックアップ化（Branchless Programming）

プロトコル解析や文字種判定などで多数の `||` や `switch` が出る場合は、`ReadOnlySpan<byte>` の静的ルックアップテーブル（C# の UTF-8 / 配列リテラル最適化によりデータセクションに直接配置される）に置き換えます。これにより **CCN が 1 になり、CPU の分岐予測ミスもゼロ** になります。

```csharp
// CCN = 1、ヒープ割り当てゼロ、分岐予測ミスなし
private static ReadOnlySpan<byte>ValidTokenChars => new byte[256] { /* 0 or 1 */ };

[MethodImpl(MethodImplOptions.AggressiveInlining)]
private static bool IsTokenChar(byte b) => ValidTokenChars[b] != 0;
```

### パターン3: ディスパッチの Source Generator 委譲

エンドポイント分岐や RPC メソッド ID の振り分けは手書きの `switch` で書かず、`Hayabusa.Generator` にコンパイル時生成させます。手書きのランタイムコードは「生成されたディスパッチャを呼び出すだけ」に保つことで、コアライブラリの CCN を常に低く維持します。
